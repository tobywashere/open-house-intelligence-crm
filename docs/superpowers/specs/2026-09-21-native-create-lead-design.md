# Native create-lead proposals with enforced identity

## Approved outcome

Keep local inference and meaningful native OpenClaw execution. Extend the verified-read milestone with one workflow: a human asks for a lead proposal, the local native agent proposes fields, the existing dashboard lets the human edit/approve/deny, and approval creates exactly one persisted lead. Rejecting creates none. Replays and restarts must not duplicate a proposal or an approved lead.

Base: `720cf521d81cf3b7ef184a796d3f83515bdf9de8`. Worktree/branch: `.worktrees/native-create-lead`, `codex/native-create-lead`. No merge, push, deployment, original-database mutation, machine-wide configuration change, or live external integration is authorized in this implementation.

## Identity and compatibility

- Reuse `X-API-Token` transport with two server-side credentials: `OHI_API_TOKEN` for the human and `OHI_AGENT_API_TOKEN` for the restricted agent. Configuring the agent token enables capability enforcement. Both must then be distinct printable ASCII, non-whitespace secrets of at least 32 characters; invalid combinations fail closed at startup and per-request.
- In capability mode the backend derives identity from the credential, never from `X-Actor`, body fields, or model output. Agent requests may read `GET /api/leads` and submit `POST /api/agent/lead-proposals` only (plus public health/auth status). Other API routes are denied, including existing mutations, approval/denial, general chat, settings, email, and integration endpoints.
- The agent proposal endpoint also explicitly requires agent identity and capability mode; a human credential or unauthenticated local/demo request cannot call it directly. Human-only native orchestration/status endpoints require human identity and capability mode.
- Existing trusted-local/demo and single-token installations remain supported when no agent token is configured, including their legacy header-based proposal behavior. The new native proposal endpoints remain disabled there. Document that this legacy behavior is not an enforced agent boundary.
- Keep CORS preflight and public `/api/health` working. Add public `GET /api/auth/status` returning only `{mode: "local"|"token"|"capabilities", role: "human"|"agent"|null}`; never return tokens. A protected dashboard unlocks only for the human role.
- Remove dashboard reliance on `VITE_API_TOKEN`: it embeds the human credential in public assets. Add a runtime unlock form and an in-memory token shared by ordinary API calls, native reads/proposals, and calendar downloads. Refresh/lock clears it; authenticated-request 401 clears it and returns to unlock. Nothing persists the token to storage or includes it in a URL. Tokenless demo still opens directly.
- New fixtures generate fresh credentials. Never reuse a human key previously shared with a legacy gateway or bundled into frontend assets. The native proposal gateway receives only the agent CRM key and its own gateway key, not the human key. The existing read plugin may use `OHI_AGENT_API_TOKEN` when supplied, retaining its legacy fallback otherwise. Its read-only operation remains unchanged.
- The legacy `scripts/setup_openclaw.py` distributes `OHI_API_TOKEN` to its gateway. It must refuse configuration whenever a nonempty `OHI_AGENT_API_TOKEN` is loaded, before invoking OpenClaw or mutating files/configuration, including dry runs. Direct `configure_openclaw` calls and CLI dotenv loading must share that guard. Preserve legacy setup when the agent token is absent. Operator docs must distinguish the native capability path from that trusted-client setup, rather than inviting capability users to rerun the legacy helper.

## Durable native proposal protocol

Reuse the existing `pending_changes` queue and transaction-safe approve/deny implementation. Add one small durable request table, rather than another in-memory receipt protocol or generic workflow framework.

1. The dashboard generates a 32-character lowercase hex request ID for an explicit create-lead proposal action. It submits `{request_id, message}` to human-only `POST /api/chat/lead-proposal`. Message length is 1–2000. Preserve the ID while checking/recovering an uncertain attempt; do not silently dispatch a new attempt on retry.
2. The backend reserves `native_lead_requests(request_id PRIMARY KEY, message, state, pending_id, created_at)` in SQLite before any model call. States: `running`, `unknown`, `failed`, `proposed`. `pending_id` is a nullable unique foreign key to `pending_changes(id)`. Reusing an ID with different text is a conflict. A repeated request with the same text returns durable status and NEVER dispatches another model run. Validate gateway configuration before reserving a fresh ID; replay/status of an existing ID must work even if the gateway is no longer configured. Every endpoint independently enforces the exact lowercase 32-hex ID format.
3. A fresh reservation makes one ordinary native OpenClaw Chat Completions request, no caller-supplied tools or finish tool. Config: `NATIVE_PROPOSAL_GATEWAY_URL`, `NATIVE_PROPOSAL_GATEWAY_TOKEN`, `NATIVE_PROPOSAL_AGENT_ID` (default `native-proposals`). Require loopback HTTP and a valid agent ID. Use user key `ohi-propose-<request_id>`, a 60-second total bound, no automatic retries, no cloud fallback in the supplied profile.
4. A separate `openhouse-proposals` plugin exposes only `openhouse_propose_lead`. Simple schema: required nonempty string `name`, optional string `email` and `phone`, no nested union/discriminator, no arbitrary URLs, operation, actor, request ID, or status arguments. The fixed handler independently validates types/lengths, derives the ID from runtime context `agent:<agent_id>:openai-user:ohi-propose-<id>`, and uses its agent credential for one fixed loopback `POST /api/agent/lead-proposals` with `{request_id, name, email?, phone?}`. The new plugin rejects registration if the human credential `OHI_API_TOKEN` is present in its environment.
5. The agent endpoint accepts only a previously reserved request in `running` or `unknown`. In one transaction, create a `create_lead` pending change (source `note`, original message as raw_text) and attach its ID to the reservation with state `proposed`. Conditionally update the still-unbound eligible row and require one updated row; rollback the insert on failure. Do not call a second extraction model. Store bounded fields (name 1–200, email at most 320, phone at most 100). A duplicate submission with identical normalized fields returns the same proposal even after a decision; conflicting fields return 409. No lead is inserted at this step.
6. After completion or error, orchestration reads the actual request/pending row from the database. It never parses model prose or trusts a model-provided proposal ID. If a proposal exists, return that verified durable status. A timeout/transport error without a durable outcome is `unknown`; a completed run without a proposal is `failed`. Late submissions after an uncertain attempt may settle it, and status checks recover them. Never label an uncertain request as safely absent or auto-retry its model call.
7. Human-only `GET /api/chat/lead-proposal/{request_id}` returns current durable state plus the actual pending record and, after approval, the stored applied result. Derive terminal `approved`/`denied` presentation from the pending row; do not duplicate decision state. At application startup atomically move unbound `running` requests to `unknown`; observed cancellation also leaves an unbound request `unknown`, without swallowing the cancellation. Never overwrite an attached proposal. Include an explicit human action to check status, not unbounded polling.
8. A human can explicitly close an uncertain request through `POST /api/chat/lead-proposal/{request_id}/close`. In one transaction, return any already-bound proposal unchanged; otherwise retire the ID by setting its state to `failed`. For an ID not yet received, insert a `failed` tombstone with an empty message: this is the sole internal exception to the message-length invariant, because no request text was received or persisted in the browser. Replay recognizes this retired empty-message row and returns its durable failed status without admitting the later body or dispatching. Received requests retain their exact original-message conflict check. Closure is idempotent, survives restart, cannot be undone by late completion/startup recovery, and makes late agent submissions fail. It does not promise to terminate an already-running gateway computation. If a proposal wins the race, the UI retains it for the existing approval/denial flow instead of claiming it was closed.

Response contract: `{request_id, state: "running"|"unknown"|"failed"|"proposed"|"approved"|"denied", proposal: PendingChange|null}`. `PendingChange` is the existing parsed database representation including its stored result when approved. All error messages are sanitized. Token values, provider responses, and private request text must not enter diagnostics.

## Human review and exactly-once application

- Keep the existing `PendingApprovals` editor/approve/deny flow, now behind human authentication. An agent credential cannot call either decision endpoint even with `X-Actor: user`.
- Reuse its transactional claim, lead insertion, stored result, and audit/outbox behavior. Approval failure rolls back both claim and mutation. Second/sequential/concurrent approvals cannot create another lead. Denial is persistent and a later approval fails.
- The new UI offers a separate “Propose lead” mode; do not broaden the read agent. Show proposed fields and explicit pending/unknown/failed/approved/denied states using database records. Reuse the existing approval dialog instead of adding an independent decision mechanism. Show a created lead only after its approved database result exists.
- Persist only a pending request identifier in session storage if needed for recovery; do not persist human credentials or duplicate private prompt text there. A refresh can unlock again and fetch status. Keep one unresolved request visible; explicit status checking must not rerun inference.
- Offer explicit Close request for uncertain/missing-status recovery. Allow a new request only after the close response confirms `failed` without a proposal, or after an ordinary terminal decision/failure. A network failure while closing preserves the original ID. Closing is a separate human action, never an automatic retry or silent abandonment.

## Validation and acceptance

Use TDD and isolated temporary databases. Required checks:

- Missing/wrong/same/malformed credentials; agent omission/spoofing of X-Actor; direct and encoded approval/denial routes; all non-allowlisted mutations; agent rejected at human orchestration and unlock; human accepted; no secrets in frontend assets.
- Normal proposal, ignored malicious completion prose/IDs, malformed tool fields, wrong runtime session identity, unreserved ID, duplicate identical request, changed-body conflict, duplicate tool submission, timeout with/without a persisted proposal, late completion, and status recovery.
- Human edits applied exactly, denial yields no lead, repeated/concurrent approval yields one lead, and pending/approved/denied states survive application/DB reopen. Existing read/browser/plugin tests stay green.
- Browser tests exercise runtime unlock and real backend proposal/approval behavior with a clearly labeled simulated model boundary. A disposable model stub is acceptable only in tests, with fixed synthetic fields, generated test credentials, clean child environments, bounded startup/teardown, and no real integrations. CI requires no OpenClaw/Ollama or credentials.

It must first run the `720cf52` read/unsupported-scope checks, then demonstrate the native proposal and human edit/approve/deny/replay/restart flow on synthetic data. Do not claim live inference here; OpenClaw/Ollama are unavailable on this Mac.

Full accounts, multi-user authorization, additional write operations, installation upgrades, broad industry scoring, and external email/calendar actions are out of scope.
